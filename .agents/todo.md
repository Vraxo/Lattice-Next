# Lattice-Next — finish the Python code-generation migration

**Mission:** remove the remaining Python-specific and task-specific code-generation shortcuts, replacing them with reusable programming semantics, world-model knowledge, and one shared language-neutral generation pipeline.

**Scope:** finish this migration before expanding programming capabilities, adding more languages, or starting other reasoning/benchmark domains. Historical baseline and completed-work notes are in [`docs/migration/python-code-generation-baseline.md`](../docs/migration/python-code-generation-baseline.md).

## Working rules

- Complete groups in order. Each checkbox should be one small, independently verifiable implementation task; split it further if inspection shows it is still too large.
- Keep changes narrow, run focused tests, and check tasks only after the change is merged and its checks pass.
- Python syntax and API facts belong in declarative language/domain knowledge. Shared Core/Runtime must remain language-neutral.
- Do not replace C# hard-codes with prompt-specific JSON rules or complete stored solutions.
- Preserve benchmark anti-shortcut rules; test changed values, identifiers, collection contents, and paraphrases.
- Do not add an LLM generator, another router, or a parallel generation engine.

Exception types, messages, and recovery bodies are fixed, no rule raises an error deliberately, and no fact distinguishes a successful result from a handled failure.
- [x] **10.5 — Represent a function declaration.** `FunctionRequirement` carries the request-derived name, ordered parameters, the declared result kind, and an ordered body of requirements; the validator requires a valid, unique name, a non-empty body, and at most eight parameters.
- [x] **10.6 — Represent function parameters.** `FunctionParameter(Name, Kind)` keeps order, requires distinct names, and makes the parameters the enclosing body's only known names, so a value kind can be inferred for them.
- [x] **10.7 — Represent a function return type.** `SemanticValueKind` (number/text/boolean) is declared once on the function and carried into the body as the enclosing result kind; an undefined kind is rejected.
- [x] **10.8 — Represent a function call.** `CallRequirement(FunctionName, Arguments)` models a call statement with ordered argument expressions; calls used as values compose through the existing `SemanticFunctionCallExpression`.
- [x] **10.9 — Represent return expressions.** `ReturnRequirement` is valid only inside a function or method whose declared result kind its value can satisfy; a return outside a declaration, or inside one that declares no result, is rejected.
- [x] **10.10 — Validate call arguments against parameters.** The validator collects declarations before validating, so a call may precede its declaration: argument count must match, and each argument's inferred kind must match the parameter's, where inference resolves literals, parameters, and calls to declared functions and treats anything unprovable as compatible. Duplicate declarations are rejected.
- [x] **10.11 — Represent a class declaration.** `ClassRequirement(Name, Fields, Methods)` carries the class identity, and the validator requires a valid name plus at least one field or method.
- [x] **10.12 — Represent fields and initialization.** `ClassField(Name, InitialValue)` keeps field order and requires distinct names and valid initial values; a field list is the constructor's initialization requirement.
- [x] **10.13 — Represent methods.** `MethodRequirement(Name, Parameters, ReturnKind?, Body)` models a method as an ordered parameter list and body with an optional result kind: a `null` result means the method returns nothing, and a return inside such a method is rejected.
- [x] **10.14 — Represent member access.** `SemanticMemberAccessExpression(Target, Member)` binds one member to its owning instance; the target is the expression's only dependency, so it satisfies the item-dependency rules of sorting and filtering, and it is classified as an arithmetic value.
- [x] **10.15 — Represent a raised error.** `RaiseRequirement(ErrorType, Condition)` models an unconditional raise or one guarded by a condition, and the condition must be boolean whenever its kind can be inferred.
- [x] **10.16 — Represent a handled error.** `HandlerRequirement(ErrorType, Body)` is not a `ProgramRequirement`, so it can only exist inside a `TryRequirement`; the validator requires a valid error type, a non-empty body, and one handler per error type.
- [x] **10.17 — Represent normal and exceptional control flow.** `TryRequirement(Body, Handlers, ResultName)` keeps the successful path distinct: the body's value can bind a result name for later requirements, while each handler describes its own recovery body. The body and handler bodies are validated at the same depth, and a handled failure composes inside a function body.
- [x] **10.18 — Realize function declarations and parameters.** The pack gains a parameterized and a nullary function header (`def name(parameter, parameter):`), both reusing the existing `function` and `arguments` bindings. - [x] **10.19 — Realize function calls and returns.** `ReturnRequirement` renders through the expression path and emits through the existing indented return forms; `CallRequirement` renders each argument through the same path, joins them positionally, and emits at its block depth, choosing the nullary call form when there are no arguments. The rendered handler reuses the declared message template, so `except FileNotFoundError:` and its recovery line come from knowledge rather than code.
- [x] **11.8 — Model serialization input and output values.** `SerializeRequirement(format, value, stream, indent)` writes one held value, and `DeserializeRequirement(format, stream, resultName)` binds the decoded value to a name the rest of the program can use; both relate a typed value to one open stream rather than to a call.
- [x] **11.9 — Model encoding.** Encoding is `SerializeRequirement` with a format name the request supplies; the pack declares which operation realizes that format (`python-json-serialize`, `matchesArgumentValue: "json"`), and held data is written by `SemanticListLiteralExpression`/`SemanticRecordLiteralExpression` using the pack’s `collectionLiteralFormat` and `recordLiteralFormat`, so no bracket, colon, or call name lives in shared code.
- [x] **11.10 — Model decoding.** Decoding is `DeserializeRequirement`, planned as an assignment inside the open stream (`python-json-deserialize`), with the resulting name entering scope for later statements.
- [x] **11.11 — Model invalid-data outcomes.** A decode failure is an ordinary handled error: `TryRequirement([FileReadRequirement([…DeserializeRequirement…])], [HandlerRequirement("json.JSONDecodeError", body)], result: null)`. The planner spells a qualified error type with the pack’s member separator, and `Plans_a_guarded_decode_with_a_named_invalid_data_failure` renders the guarded read, the decode, and the recovery output.
- [x] **11.12 — Move file API signatures into declarative language/domain knowledge.** No shared-code conditional names a file API any more: `open`, the read and write modes, `encoding="utf-8"`, `sys.argv`, `os.scandir`, `sorted`, `is_file`, and `st_size` all come from pack productions and operations (`bound-with-open-read-statement`, `bound-write-with-open-statement`, `bound-directory-iteration-statement`, `programArgumentFormat`), and the requirement model only names effects, paths, streams, and formats.
- [x] **11.13 — Move serialization API signatures into declarative knowledge.** `json.dump` and `json.load` appear only in `indented-serialize-statement` and `indented-deserialize-statement`; the format name (`json`) is request data matched by `matchesArgumentValue`, the indentation is a declared value, and `recordLiteralFormat` spells `{"name": "Ada", "age": 36}`.

## Definition of done

The migration is complete only when:

- Requests become language-neutral semantic goals/requirements before target-language realization.
- Programming operations, relationships, and effects are reusable world-model/knowledge-base content, not task handlers or prewritten solutions.
- Python syntax/API facts remain declarative; shared Core/Runtime has no Python-specific parsing, validation, or generation branches.
- No complete or near-complete benchmark solution is stored in sequence rules, packs, code, or task-ID templates.
- Python and the minimal second language use one production generation mechanism.
- Changed values, identifiers, collections, and equivalent phrasings generate correct executable programs.
- Benchmark anti-shortcut requirements are satisfied.
- Release build, full .NET tests, external-tool tests, and applicable generation/behavioral tests pass.

**Deferred until completion:** broader programming ontology expansion, languages beyond the minimal proof, additional reasoning domains, and general benchmark expansion.
