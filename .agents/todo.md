# Lattice-Next — agent implementation queue

This is the active, ordered queue for the dedicated coding agent. It replaces the old mixed historical checklist with PR-sized work that advances the current reasoning frontier. All checklist items are deliberately flat: no nested tasks.

**Baseline:** `main` at `a5c426214ed3f448443b737a70b9173645fe89fe` (PR #551 merged, November 23, 2026).

## How to work this queue

- Work from the latest `main` and follow the order below unless a concrete dependency or correctness defect requires changing it.
- Treat each checkbox as one focused, independently reviewable pull request. Multiple coherent commits are fine inside that PR; do not combine unrelated checkboxes.
- Before implementing an item, inspect the current code and tests. Reuse existing semantic and class-expression machinery wherever it already provides the required behavior; do not build a duplicate engine.
- Each PR must include focused tests, relevant documentation, a Release build, and the applicable test suites. Report exactly what ran and whether it passed.
- Enable GitHub auto-merge on every PR and let the configured checks govern merging. Never bypass CI or merge manually as a workaround.
- Check an item only after its PR is merged and the required checks pass. Add the merged PR number to the item when checking it off.
- If an item is already implemented when inspected, prove that with focused tests and update the item into a verification/documentation task rather than reimplementing it.
- If an item proves too large for one review, split it into adjacent flat checklist items before starting implementation.
- Preserve open-world semantics: missing facts are Unknown, not negative evidence. Preserve contradictions, witness scope, and provenance in both answers and proofs.
- Do not add domain-specific reasoning branches, concept-specific handlers, task-ID dispatch, stored prose definitions, or benchmark-specific answer templates. Put domain facts in declarative knowledge and make the reasoning reusable.
- Do not use an LLM judge or an execution/handled count as a substitute for human semantic or answer-quality review.

## 2. General multi-variable relational joins

- [ ] **J-01 — Add a join acceptance fixture before generalizing inference.** Create a small declarative dependency graph for a service-outage investigation: for example, an application depends on an API, the API depends on a database, and an observation reports the database unavailable. Include a branching path, a disconnected path, an incomplete path, and conflicting or explicitly negative evidence. Specify the exact expected bindings, conclusions, Unknown cases, and proof sources without adding an outage-specific handler.
- [ ] **J-02 — Implement a generic scoped-variable join matcher.** Generalize the existing existential witness matching into reusable matching over arbitrary declared relations and scoped variables. Support ordered relation arguments, shared-variable equality, multiple candidate bindings, and independent witness scopes. The matcher must not branch on predicate names or be limited to the current nested-witness record shape.
- [ ] **J-03 — Use joined relational premises in quantified rules.** Allow a rule to require multiple relational premises connected by shared variables, not only unary premises, fixed concrete objects, or the current bounded existential-premise form. Every premise must match one consistent variable assignment; unrelated facts must never be combined into a false join.
- [ ] **J-04 — Allow conclusions to reuse bound variables.** Extend quantified rule conclusions so a derived relation can refer to variables bound by the rule's premises, rather than requiring every relational conclusion object to be a fixed concrete individual. Validate that every conclusion variable is bound, preserve argument order, and reject unbound or out-of-scope variables.
- [ ] **J-05 — Support branched and longer join patterns.** Test patterns with at least three variables, more than two relation premises, branching, converging paths, and a variable shared by several premises. Keep the implementation generic; a linear-chain-only algorithm is not sufficient, and no transitive closure may be inferred unless an explicit rule or query asks for it.
- [ ] **J-06 — Add explicit negative relational premises over bound variables.** Match a negative relational condition only against explicit negative evidence for the same predicate and exact bound arguments. Preserve True, False, Both, and Unknown behavior; never infer a negative relation from the absence of a positive edge.
- [ ] **J-07 — Preserve complete provenance across joins.** Every derived result must retain the rule source and all supporting facts for its binding. Preserve distinct acyclic proof alternatives when the same conclusion has independent support, deduplicate semantic results without dropping evidence, and prevent cyclic rules from manufacturing circular proofs.
- [ ] **J-08 — Make join evaluation deterministic and bounded.** Add or improve relation lookup/indexing and join ordering so larger graphs do not require naive unrestricted Cartesian products. Define deterministic work limits and an explicit outcome for exhausted limits; never present a truncated search as a complete negative answer or as proof of Unknown.
- [ ] **J-09 — Expose supported joins through ordinary language.** Extend the native parser and query path only for constructions whose semantics are now implemented. Add exact formula tests, end-to-end inference tests, multi-sentence/context tests where relevant, and safe rejection tests for unsupported quantifier combinations. Do not add a phrase-specific path that bypasses the shared semantic model.
- [ ] **J-10 — Explain joined answers as proof paths.** Render which individuals were bound to each variable, which relations connected them, and which evidence supports the conclusion. Disconnected, ambiguous, contradictory, or incomplete paths must be explained as such rather than collapsed into a confident answer.

## Completion standard

A checkbox means the behavior is implemented, tested, documented, merged, and verified on the resulting `main` baseline. A green build alone is not sufficient for a reasoning feature: tests must cover exact semantics, same-witness binding, disconnected relations, open-world Unknown, explicit negative evidence, contradictions, provenance, and safe rejection wherever they apply.
